# 005: Conflict detection field

Use Drive `md5Checksum` as the Google adapter's content version token for plain-text entries. Human-reported S4 results on 2026-10-08 showed that all four candidates (`version`, `modifiedTime`, `md5Checksum`, and `headRevisionId`) changed on a content edit and detected a stale snapshot. API and manual Drive renames changed `version` and `modifiedTime`, while `md5Checksum` and `headRevisionId` stayed stable. Choose the checksum because it represents the protected content directly and avoids the observed rename conflicts. Keep `journal.Version` opaque and provider-independent; the Google adapter owns field interpretation. See `docs/development/findings.md` for the measured evidence.

This selects the field, not an atomic write protocol. A metadata comparison before uploading does not close the check/update race, and identical final bytes have the same checksum even after an A→B→A history. The experiment covered one content edit and two renames for one test account; sharing changes and production concurrent writes remain unverified. Production storage must reject or handle a missing checksum explicitly rather than treating an empty token as valid. The Google provider remains disabled until its remaining implementation and acceptance checks pass.

## Integrated adapter boundary (2026-10-10)

The Drive adapter now serializes mutations across request-scoped stores using bounded account lock stripes, compares md5Checksum immediately before updating, suppresses unchanged uploads, and verifies the acknowledged upload checksum. Missing checksums fail closed. Reads also compare downloaded bytes with the listed checksum so a concurrent content change cannot produce a falsely paired body/version.

If Drive metadata supplies an ETag header, the adapter forwards If-Match and maps 412 to a conflict. A synthetic test proves forwarding and rejection with a mocked server; it does not establish Drive v3 conditional media-upload support. External writers can still race the read/upload gap when no verified precondition is available. New-file creation also lacks an external atomic uniqueness guarantee. GOOGLE_TEST_MODE allows only controlled localhost validation; production remains blocked pending a verified concurrency policy. No complete stale-write guarantee is claimed from these process locks/checksum comparisons.
