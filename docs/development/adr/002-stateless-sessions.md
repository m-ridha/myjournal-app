# 002: Use encrypted signed cookie sessions

The app keeps session state in an encrypted, signed HttpOnly cookie instead of a database-backed server-side session. This matches the requirement to avoid storing journal content server-side while still carrying the provider connection and refresh token through the app lifecycle.

On 2026-10-08, the user adopted a fixed 30-day session lifetime, following the S7 lifecycle experiment. Enforce the deadline using the original `IssuedAt` as well as cookie expiry; access-token refresh must not extend it. Server-side age validation and matching cookie Expires/Max-Age were implemented on 2026-10-09 for the app, with injected-clock boundary tests. Production Google remains disabled. The lifetime may be revised to one or two weeks during development. When shortening it, server-side age validation must also apply the new limit to existing cookies, even if their browser expiry is later.

## Pending authorization (2026-10-10)

Remote login uses a separate `mj_oauth` HttpOnly, SameSite=Lax cookie at `/api/v1/auth/`, with configured Secure policy and a fixed ten-minute age checked on the server. Three independent 32-byte random values supply state, PKCE verifier, and OIDC nonce. The existing AES-GCM codec is reused with distinct authenticated purpose data; authenticated session encoding remains compatible. The pending cookie never becomes an authenticated session by itself.

Callback handling validates provider binding, issuance/expiry, and constant-time state equality, rejects missing/duplicate code/state or provider error responses, and clears the pending cookie before exchange. Failures preserve existing sessions and drafts. Local development's intentionally synthetic login is exempt. Google authorization uses the retained verifier's S256 challenge and `/api/v1/auth/google/callback`; exchange/claim validation was initially unfinished at this foundation step. The integrated implementation below supersedes that status; production registration remains disabled pending live acceptance.

A new login replaces the browser's pending transaction, so parallel login tabs may require restarting sign-in. Cookie deletion consumes the normal browser flow but is not a server-side replay ledger: a copied encrypted transaction remains decryptable until expiry. Provider authorization-code single use and PKCE must also be enforced during the eventual exchange. No server-side session store or new dependencies were introduced. HTTPS/Console and live browser OAuth acceptance remain separate.


Integrated Google credentials now use a versioned small JSON payload containing only subject and refresh token, encrypted inside the existing session cookie. Access tokens/ID tokens are excluded from credentials; access-token memory is bounded to 128 entries keyed by a refresh-token digest and shared across request-scoped stores. Refresh never updates session IssuedAt. Omitted refresh tokens are recovered only from a validated same-account previous connection; a different Google account on reconnect is rejected. If a future refresh response rotates a refresh token, the current adapter fails closed and requires reconnect rather than losing the replacement on restart. Cookie values over 3600 bytes are rejected before setting the session. Real cookie-size and browser lifecycle acceptance remain in google-live-checks.md.
